# Подпись и публичный релиз

PlatScope использует два независимых механизма доверия. Их нельзя смешивать:

- **подпись обновлений Tauri** подтверждает, что пакет выпущен владельцем ключа PlatScope; приложение отклоняет пакет с неверной подписью;
- **Authenticode** подтверждает издателя Windows для SmartScreen. Коммерческого сертификата Authenticode пока нет, поэтому первый установщик может показывать предупреждение «Неизвестный издатель».

SHA-256 в `SHA256SUMS.txt` помогает вручную проверить загрузку, но не заменяет ни один из этих механизмов.

## Каналы сборки

`package.yml` остаётся ручным QA-каналом с `contents: read`. Он не получает ключ обновлений и не создаёт GitHub Release.

`release.yml` запускается только для тега `v<version>`, сверяет тег с `tauri.conf.json`, выполняет quality gate, собирает Windows NSIS, подписывает updater artifact и публикует:

- установщик `.exe`;
- подпись Tauri `.sig`;
- `latest.json` для встроенного updater;
- `SHA256SUMS.txt`.

Первый updater-совместимый релиз — `0.1.21`. Более ранние версии не умеют читать `latest.json`, поэтому переход с `0.1.20` выполняется ручной установкой. Начиная с `0.1.21`, приложение проверяет обновления при запуске и затем каждые шесть часов; установка требует явного подтверждения.

## Ключ обновлений

Приватный ключ и пароль не хранятся в Git, workflow YAML, cache или artifacts. CI получает их только из GitHub Secrets:

- `TAURI_SIGNING_PRIVATE_KEY`;
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.

Публичный ключ находится в `tauri.conf.json` и не является секретом. Локальная резервная копия приватного ключа хранится вне репозитория в профиле Windows; пароль сохранён через DPAPI и читается только той же учётной записью Windows.

Обычные quality и QA jobs не получают signing secrets. Pull request из fork не имеет к ним доступа.

## Порядок релиза

1. Обновить версии в корневом `Cargo.toml`, `apps/desktop/package.json` и `tauri.conf.json`.
2. Выполнить formatter, lints, Rust/frontend tests и сборку.
3. Создать и отправить тег `v<version>` на проверенный commit `main`.
4. Дождаться успешного `release.yml`.
5. Проверить, что GitHub Release не является draft, а `latest.json` содержит нужную версию, URL NSIS и непустую подпись.
6. Скачать опубликованный установщик и сверить SHA-256.

Пока нет Authenticode-сертификата, release notes обязаны прямо предупреждать о возможном SmartScreen. Такой релиз допустимо называть подписанным для встроенного updater, но нельзя называть установщиком от подтверждённого Windows-издателя.

## Ротация и компрометация

При подозрении на утечку публикация останавливается, GitHub Secrets заменяются, скомпрометированный релиз удаляется из канала `latest`, а пользователям сообщаются затронутые версии. Новый публичный ключ нельзя незаметно доставить через скомпрометированный старый канал: его нужно выпустить в вручную устанавливаемой версии и явно описать миграцию.

Удаление локальной резервной копии до проверки восстановления из защищённого backup запрещено: потеря приватного ключа лишит установленные версии возможности принять новые обновления.
