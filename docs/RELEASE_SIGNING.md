# Подпись и доверенный релиз

Этот документ задаёт обязательную границу между внутренней QA-сборкой и публичным релизом PlatScope. Наличие установочного файла или SHA-256 не означает, что файл подписан или получен от доверенного издателя.

## Каналы сборки

### Внутренняя QA-сборка

Ручной workflow `package.yml` собирает неподписанные NSIS и AppImage с `contents: read`, создаёт `SHA256SUMS.txt` и сохраняет всё только как workflow artifacts. Такие файлы подходят для внутренней проверки, но:

- не публикуются как GitHub Release;
- не называются доверенными или подписанными;
- не используются как источник auto-update;
- могут показывать предупреждение ОС о неизвестном издателе.

SHA-256 обнаруживает случайную порчу или подмену относительно отдельно полученного ожидаемого хэша, но не удостоверяет издателя.

### Доверенный публичный релиз

Публичный релиз разрешён только после выполнения всех условий:

1. commit и версия однозначно связаны с защищённым release tag;
2. quality gate прошёл для этого commit;
3. Windows installer подписан Authenticode сертификатом издателя и содержит доверенную временную метку;
4. для Linux опубликованы SHA-256 и выбранная detached signature, проверяемая документированным публичным ключом;
5. подписи и хэши проверены отдельным шагом после упаковки;
6. публикация выполняется из защищённого CI environment после ручного подтверждения;
7. release notes явно перечисляют версии, платформы, имена файлов и SHA-256.

До появления сертификата, ключей и защищённого release environment этот канал не существует.

## Хранение ключей

- private keys и пароли никогда не хранятся в репозитории, workflow YAML, cache, build artifacts, логах или локальных `.env`;
- предпочтителен неизвлекаемый ключ в HSM или управляемом signing service; экспортируемый сертификат допустим только как временный переход с минимальным сроком жизни;
- signing credentials доступны только защищённому release environment и недоступны pull request из forks;
- environment требует ручного approval и ограниченного списка maintainers;
- quality jobs и обычный packaging workflow не получают signing secrets;
- доступ, выпуск, ротация, истечение и отзыв ключа должны оставлять аудируемое событие.

Имена CI secrets и конкретный signing provider фиксируются одновременно с подключением реального хранилища. Пустые или тестовые secrets в репозиторий не добавляются.

## Порядок релиза

1. Проверить согласованность версии в Tauri config и release tag.
2. Выполнить полный deterministic quality gate.
3. Собрать artifacts из tagged commit.
4. Подписать artifacts внутри защищённого release environment.
5. Проверить подпись, временную метку, identity издателя и SHA-256 уже подписанного файла.
6. Опубликовать immutable artifacts и checksums.
7. Скачать опубликованные файлы в чистом verification job и повторить проверку.

Windows-проверка выполняется через `Get-AuthenticodeSignature` и должна завершаться статусом `Valid`. Хэш считается после подписи, потому что Authenticode изменяет файл. Для AppImage минимум проверяется командой `sha256sum -c SHA256SUMS.txt`; механизм detached signature и публичный ключ должны быть утверждены до первого Linux-релиза.

Локальный artifact preflight реализован в `scripts/verify-release-artifacts.ps1`:

- `-Mode Qa` проверяет наличие и SHA-256 Windows/companion artifacts, companion permissions/CSP и явно показывает `NotSigned`/отсутствующий AppImage как предупреждения;
- `-Mode Trusted` не допускает эти предупреждения, требует `Valid` Authenticode, signer/timestamp certificates, AppImage и detached signature через утверждённый `release-signing-keyring.gpg`/`gpgv`;
- успешный preflight доказывает только свойства переданных файлов. Он не доказывает protected tag, успешный CI для commit, права release environment или неизменность после публикации — эти условия проверяются отдельно по порядку выше.

## Auto-update

Updater остаётся выключенным, пока нет доверенного публичного канала. Его подключение — отдельное изменение с обязательными условиями:

- manifest доставляется только по HTTPS;
- каждый update artifact проверяется встроенной криптографической подписью, а не только checksum;
- ключ обновлений отделён от WFM credentials и от ключей пользовательских данных;
- приложение не устанавливает обновление при ошибке подписи, schema или version policy;
- пользователь может отказаться от обновления и скачать installer вручную;
- предусмотрены ротация ключа, отзыв скомпрометированного релиза и восстановление с последней доверенной версии.

Наличие подписанного installer само по себе не разрешает auto-update: сначала нужны подписанный release channel, проверяемый manifest и отдельная модель восстановления.

## Компрометация

При подозрении на утечку выпуск останавливается. Maintainer отзывает или блокирует credential у провайдера, удаляет скомпрометированные artifacts из канала, публикует уведомление с затронутыми версиями и только после ротации ключа повторяет сборку из проверенного commit. Старый ключ не используется для «исправляющего» релиза.
