# Как отличить тайник Гринир от обычного шкафчика

## Результат

В записи `warframe-binary-20260912T092700684110700Z` найдены **три размещённых тайника миссии** с той же моделью `GrnStorageLocker_skel.fbx`, что у **103 размещённых обычных шкафчиков**. Ещё один экземпляр типа тайника имеет нулевые координаты и является шаблоном; в число целей он не включён.

Модель не определяет назначение контейнера. У тайника подтверждены два отличия в свойствах производного типа:

- В `ServerChildren` указан `Type=CacheLockerReplicatedHitSwitch`.
- В `OverrideMaterial` указан `/Lotus/Objects/Grineer/Structural/Doors/GrineerDoorHatchWhiteCache`.

У обычных шкафчиков используются `LockerAttachments/LockerReplicatedHitSwitch` или `LockerAttachments/LockerReplicatedHitSwitchRare`. **Суффикс `Rare` здесь нельзя использовать как признак искомого тайника:** в этой записи он встречается у 43 обычных размещённых шкафчиков. Остальные 60 имеют вариант без суффикса. В свойствах обеих групп нет ссылки на `CacheLockerReplicatedHitSwitch`.

## Подтверждение через действие открытия

У двух закрытых тайников в первых снимках найден реальный дочерний `ContextAction`. Его адрес, метаданные и обратный handle проверены. Свойства действия:

```text
CompleteScript={
Script=/Lotus/Scripts/SabotageCaches.lua
Function=CacheStorageLocker
...
_nativeFaction=Grineer
_cacheSpawnTag=SabotageCacheGrineer
}
Action=HIT_SWITCH
ActionText=/Lotus/Language/Game/OrokinSabotageOpenCache
DestroyOnUse=1
```

В дочерних ресурсах этого действия также указаны `CacheLight`, `LootMarkerInfo` и звук `/Lotus/Sounds/Objects/StorageContainer/StorageContainerHiddenLoopASeq`. Это согласуется с назначением тайника. Само наличие звука в свойствах не означает, что он сейчас воспроизводится.

Таким образом, определён именно тайник миссии, а не произвольный контейнер, в имени которого встретилось слово `Rare`.

Пользователь сообщил, что открыл два тайника: один до записи и один во время; третий не нашёл. Снимки 1–5 согласуются с этим описанием:

| `0x26193f2a310` | 285,71234 | −23,51897 | 230,61194 | В снимках 1–4 действие открытия присутствует; в снимке 5 исчезает, меняется состояние анимации |

**Оставшийся закрытый тайник в этой миссии — третий в таблице.** Вывод основан на действии открытия, переходе второго тайника и сообщении пользователя, а не на подборе трёх объектов по количеству.

Снимок 4 записан 16:30:08–16:30:19, снимок 5 — 16:31:04–16:31:14 по местному времени UTC+7. Изменение произошло между чтениями объекта в этих снимках; точное время открытия запись не даёт.

В снимке 6 два из трёх прежних объектов уже не проходят проверку идентичности: в архиве резко сокращается число сохранившихся экземпляров. **Это нельзя трактовать как открытие ещё двух тайников.** Для вывода о найденном последнем тайнике используется состояние снимка 5. Координаты относятся к этой записи и не переносятся на новую миссию.

## Как воспроизведено

Исследование выполнено локально по завершённым архивным снимкам, без чтения работающей игры и без создания нового дампа.

1. Первоначальная выгрузка штатным `spatial_archive` снимка 6 показала лишь часть прежних объектов. Поэтому последние сохранившиеся шкафчики не использовались как полная выборка миссии.
2. Выполнен один проход по 109 719 уникальным сжатым блокам всех шести снимков. Каждый распакованный блок проверен по размеру и SHA-256; ссылки на один блок используются повторно для соответствующих снимков.
3. Найдены кандидаты по проверенным таблицам `Decoration` и нескольких семейств действий. Для каждого проверены native-header и обратная ссылка handle. Метаданные декодированы со словарём Zstandard с ранее проверенным SHA-256.
4. Для шкафчиков сравнивались полные свойства производного типа и родителей. Ненулевые координаты и двусторонняя связь с типизированным `Zone` подтверждены для всех 106 размещённых шкафчиков первого снимка.
5. Три тела тайников сравнены адресно между снимками, строго в пределах размера `Decoration` — `0xAF0` байт. Дочерние действия читались через ограниченный массив, затем проверялись как отдельные объекты.

Локальные воспроизводимые материалы находятся в `target/grineer-locker-analysis-20260912/`: `source.txt`, `scan.py`, `scan-summary.json`, `type-chains.json`, `cache-instances.json`, `cache_children.py`, `cache-children.json`. Они намеренно остаются в игнорируемом каталоге; двоичные данные в Git не добавляются.

## Технические опорные точки этой версии игры

Эти адреса — свидетельства конкретной записи, а не константы для нового запуска игры:

- Метаданные тайника: `0x2611d82b7b8`.
- Метаданные действия тайника: `0x2611d82b658`.
- Таблица действий в этой записи: `0x7ff66a12cf68`. Она отличается от базовой таблицы `ContextAction`, поэтому поиск только базовой таблицы пропускает действие; наследование подтверждается через метаданные.
- В теле `Decoration` по `+0x3B0` находится массив ссылок: указатель, используемый размер в байтах, ёмкость в байтах. В проверенных закрытых тайниках размер равен 16 байтам, после открытия — 8. **Размер сам по себе не является универсальным флагом открытия.**
- В исследованных закрытых тайниках первая ссылка массива ведёт через handle на подтверждённый `ContextAction` с `CacheStorageLocker`. После открытия во время записи эта ссылка исчезает из массива.
- Поле `+0x1E8` меняется от общего пустого значения на значение, совпадающее с ресурсом анимации по `+0x4B8`. Это дополнительное свидетельство перехода, а не универсальный булев флаг.

## Правило для будущего распознавания и фильтра карты

Назначение и состояние должны определяться отдельно:

1. **Тип «Тайник Гринир»**: подтверждённая `Decoration` с этой моделью, сочетанием материала `GrineerDoorHatchWhiteCache` и дочернего `CacheLockerReplicatedHitSwitch`, ненулевой позицией и проверенным `Zone`. Читать соответствующие верхнеуровневые блоки свойств с учётом переопределений, а не искать подстроку `Rare` по всей цепи.
2. **Подтверждённое действие открытия**: реальный дочерний объект, корректные handle/метаданные и сочетание `SabotageCaches.lua`, `CacheStorageLocker`, `OrokinSabotageOpenCache` внутри соответствующих блоков. Это позволяет отличить сохранившийся закрытый тайник от открытого по этой записи.
3. Отсутствие действия при ошибке чтения, разрушении объекта или переходе миссии должно давать неизвестное состояние. Само по себе отсутствие дочернего объекта не доказывает открытие.
4. В идентичности пользовательского фильтра нужен стабильный смысловой признак тайника: один `Mesh` объединяет его с обычными шкафчиками. Адрес, координаты и динамическое состояние открытия в сохраняемый фильтр не включать.
5. После первоначального обнаружения достаточно адресного чтения тела и малого массива дочерних ссылок. Для такого различения не требуется периодически сканировать гигабайты памяти или записывать новые дампы.

Результаты исследования внедрены в 0.1.80: отдельный тип тайника, адресная проверка состояния и общий механизм вариантов объектов для фильтров.
